# ADR-0033：以「分段解析 + 预览确认」把长篇设定导入为新世界

- 状态：proposed（2026-10-21，待作者裁定；未裁定前不改变任何既有 canon）
- 关联：ADR-0004（SQLite 内容持久化）、ADR-0009（内容库迁移）、ADR-0025（canon 约束落点）、ADR-0029（六层提示词与 preset 投影）、ADR-0030（账号与每日配额）、ADR-0031（多世界与资料组）、ADR-0032（整库导入导出）
- 影响面：新增 `lore-import.mjs`；`server.mjs`（两个新端点）；`dist/index.html`、`dist/app.js`、`dist/styles.css`；`Dockerfile`；`package.json`；静态文档；两组新测试

## 背景

作者目前有两种把设定放进资料库的方式：

1. 在资料编辑器里逐条手写，或让设定助手按内容块生成单条候选；
2. 「设置 → 数据管理」里的整库导入，但它要求先有一份 `worldforge-export` 交换格式的 JSON。

两者都不适合「把已有的几万字设定（世界设定、人物小传、势力介绍、年表……）一次性搬进产品」。作者需要的是：**粘贴原文 → Agent 解析并改写成项目支持的资料格式 → 作者过目 → 建立新世界**。

这件事必须在不破坏既有纪律的前提下完成：

- 六层提示词与 preset 投影只能替换第 2 层（ADR-0029）；
- 所有新内容只能是 `proposed`，`canon` 由作者裁定（ADR-0025、`AGENTS.md`）；
- 产品没有默认世界，世界由作者建立，编号取最小可用 `W##`；
- 内容写入只有一条真值通道：整库快照 + `expectedRevision` 乐观锁，SQLite 与 PostgreSQL 共用；
- 模型调用是付费的，且每人每天有 AI 配额（ADR-0030），长文不能假装免费；
- Docker 镜像用显式白名单 `COPY`，新增模块必须登记。

## 决策

### 1. 两个端点：解析不写库，确认才写库

- `POST /api/lore-import/parse`：只生成、只读内容库（用于分配世界编号），**不写任何数据**。
- `POST /api/lore-import/commit`：要求自定义请求标记头 `x-worldforge-lore-import: 1`，把作者确认过的计划**追加**进内容库，复用 `contentStore.replace` 与 `expectedRevision` 乐观锁。

理由：预览是作者主权的落点；如果把「调用模型」和「写入正史」合成一步，一次不理想的解析就会直接污染资料库。分成两步也让前端能显示条目清单、统计与告警，并让作者取消其中任意条目。

### 2. 输入边界与计费口径

| 限制 | 值 | 说明 |
| --- | --- | --- |
| 单次原文上限 | 90 000 字符 | 超出按段落边界截断并明确告警 |
| 每段字符数 | 9 000 | 只在该窗口内找段落 / 换行 / 句末断点 |
| 最多段数 | 10 | 与上限同源；再多也不继续切 |
| 每段条目上限 | 16 | 防止一段塞进整部族谱，也限制单次输出的体积 |
| 单次总条目上限 | 160 | 超出保留前 160 条并告警 |
| 并发段数 | 3 | 串行太慢、全并发容易触发上游限流 |
| AI 配额 | 每段 1 次 | 调用模型前 `chargeQuota('ai')`；配额不足整次失败 |

切分是**确定性**的：同样的输入永远得到同样的分块与断点，便于复现和测试。

### 3. 目标格式就是现有资料格式，不新增字段

模型只被要求输出一个中间形状（类型、名称、概述、正文、三个要点、约束、开放问题、标签、关联名称、地理层级与上级名称、编年史容器 / 节点 / 纪年 / 排序、事实层次），服务端再把它改写成资料库已有的形状：

- `values`：组字段（`summary`、`details`、`attributeA/B/C`、`constraints`、`openQuestions`）；
- `location`：`kind` / `parentId`（层级集合与 `dist/geography.js` 一致）；
- `chronicle`：`kind` / `parentId` / `dateLabel` / `order`；
- `relationIds`：按条目名称解析成稳定 ID；
- `status` 固定 `proposed`，`truthScope` 只接受三档，背景故事固定 `unknown`。

类型收敛到五种：`character`、`location`、`timeline`、`story`、`info`。势力、种族、文化、宗教、力量体系、技术、物品、事件等一律进 `info`，分类写进 `attributeA`；`info` 是本世界的自定义资料组，随世界一起落库（组数达 40 上限时只读派生、不落库并告警）。

编号沿用仓库约定：`CHR/LOC/EVT/STY/INF-W##-###`，世界编号取最小可用 `W##`（与浏览器端 `WorldforgeWorldScope.nextWorldId` 同一规则）。

### 4. 跨段合并不调用模型

同名同类型视为同一实体：保留首条、补充缺失字段、合并正文（包含关系取长者，否则换行拼接）、并集约束 / 开放问题 / 标签 / 关联。世界名与概述取第一段非空值。

不额外做一次 LLM 归并，因为那会多一次付费调用、多一个失败面，并且让「合并结果」不可复现。

### 5. 结构缺口只告警，不替作者发明设定

- 编年史节点找不到容器时，用**原文给出的容器名称**补建一个容器（结构必需，且名称不是新造设定）；
- 地理条目找不到上级、节点找不到编年史时，保留 `kind`、清空 `parentId`，条目进入「待整理的地理条目 / 编年节点」；
- 关联名称解析不到、跨段重复、原文截断、某段解析失败，一律进 `warnings` 并在预览里显示。

### 6. 提示词分层与 preset 解析

- 第 1 层：产品安全边界（既有）。
- 第 2 层：`agent-settings.json` 里「设定助手」入口选定的 preset（`resolveSurfaceProfile('lore', …)`）；未知或不兼容的 preset 在调用模型前返回 400。
- 第 3 层：新增入口契约 `LORE_IMPORT_ENTRY_CONTRACT`（与 `ai-harness.mjs` 的其它契约同级，定义在 `lore-import.mjs`，因为只有本功能使用）。
- 第 4 层：作者保存的统一个性化风格提示。
- 第 5 层：本次任务、五种类型的判定规则、**写死的 JSON 外壳**（兼容接口会忽略 `json_schema`）、作者补充要求。
- 第 6 层：原文与补充要求只出现在用户消息侧；原文里的 `</worldforge_import_source>` 会被打断，避免撑破标签。

### 7. 与既有导入的分工

| | `POST /api/import`（ADR-0032） | `POST /api/lore-import/commit`（本 ADR） |
| --- | --- | --- |
| 输入 | 整库交换格式 JSON | 预览里确认过的资料计划 |
| 语义 | `merge` / `replace` 整库覆盖 | 只追加一个新世界及其资料 |
| 权限 | 仅管理员 | 登录用户（与 `PUT /api/content` 同级） |
| 触达范围 | 资料、卡牌、关键词、资料组、备注、美术 | 资料条目与可选的自定义资料组 |

### 8. 不自动晋升 canon，也不写 Git

导入结果全部 `proposed`，不会写回仓库里的 Markdown 设定，也不会触发世界发布（World Package）。作者在编辑器里逐条裁定后，仍按既有归档流程进入 `worlds/` 与 Git。

### 9. 文件上传：先在本地把文档读成文本，再走同一条解析管线

作者还要能上传 `.docx` / `.doc` / `.xlsx` / `.md` / `.zip` / `.rar` 等文件。这被实现为**解析之前的独立一步**（`POST /api/lore-import/extract`，`lore-import-files.mjs`），理由：

- 文件解析不调用模型、不写库、不计配额，因此可以和「按段计费的解析」彻底分开；
- 抽取出的文本会回填到对话框的原文框里，作者可以先删改、再决定是否花配额解析；
- 一篇 200 页的 docx 抽出来可能超过 9 万字的解析上限，先展示再裁剪比「一次上传直接截断」可控。

支持矩阵与代价：

| 格式 | 处理方式 | 质量与代价 |
| --- | --- | --- |
| `.md` / `.txt` / 其它可读文本 | UTF-8（含 BOM）→ UTF-16LE/BE → GBK 依次回落 | 完整；GBK 覆盖 Windows 记事本另存的文本 |
| `.docx` | OOXML 即 ZIP + XML：读 `word/document.xml` 与脚注/尾注，保留段落、表格单元格与制表符 | 完整；不处理批注、页眉页脚与图片 |
| `.xlsx` | 读 `sharedStrings.xml` + `workbook.xml`/`rels` + 各工作表 XML，输出「表名 + 行×列」的制表符文本 | 完整到文本层面；日期等格式化的数值仍是原始序列值 |
| `.zip` | 逐条目校验扩展名白名单（md/txt/docx/doc/xlsx/xls/rtf/zip），只抽取允许的类型，允许一层嵌套 | 内部不可导入的文件、加密条目、路径不安全条目一律跳过并在预览里告警 |
| `.doc` / `.xls` | OLE2 旧版二进制：扫 UTF-16LE 文本段（两种字节对齐按高频汉字/标点打分），必要时回落到单字节 GBK 扫描 | **尽力抽取**，可能混入域代码、页眉或顺序偏差；固定追加告警要求作者核对 |
| `.rtf` | 去控制字与分组，`\uN` / `\'hh` 按 GBK 解码 | 只取纯文本，格式与表格丢失 |
| `.rar` | 识别 RAR4/RAR5 签名后**明确拒绝** | RAR 是专有压缩格式，零依赖无法解压，也不引入第三方库或外部命令；提示改用 ZIP 或粘贴文本 |
| `.pdf` | 识别后明确拒绝 | 同上；即使能抽文本也需要字体与版面处理，不在本次范围 |

预算统一由 `LORE_IMPORT_FILE_LIMITS` 收口：8 个文件、单文件 12 MB、合计 24 MB、抽取文本 120 000 字、压缩包 200 条目、单条解压 8 MB、总计解压 24 MB、嵌套 2 层；请求体上限 48 MB（base64 膨胀）。

安全边界：

- 解压内容**只在内存里**处理，从不落盘，因此 ZIP 路径穿越只影响显示名；条目名仍按「相对路径、无 `..`、无绝对路径/盘符」过滤。
- 解压量按**实际输出**限制（`zlib.inflateRawSync` 的 `maxOutputLength`），不信任中央目录声明的长度；声明值另做一次上限检查。
- 加密条目跳过；ZIP64、分卷、非 deflate/store 压缩算法直接拒绝，不做静默降级。
- 端点要求 `x-worldforge-lore-import: 1` 标记头（与 commit 共用），避免跨源表单直接提交；不计配额，但读取量受上面的字节预算约束。

明确不做：RAR 解压、PDF 解析、图片 OCR、旧版 `.doc` 的正式格式解析。这些都需要新的依赖或外部工具，超出「零依赖 + 可审查」的部署边界；作者可以另存为 `.docx` / `.md` 或直接粘贴文本。

### 10. 解析 agent 不负责 JSON：记录格式 + 通用规范化层

实测（`deepseek-flash`）暴露的问题不是「模型不会整理设定」，而是「模型同时被要求写合法 JSON」：字符串里漏转义换行、输出到上限被截断、偶尔整段返回空内容。任何一处语法错误都会让**整段**丢弃，表现为「1 段 → 0 条资料」。

因此把职责拆开：

- **解析 agent 只负责识别、抽离、建立条目**。第 5 层的输出契约改成人类可读的记录格式：`@@ 世界` / `@@ 条目` 段落 + `字段：值` 行，正文可自然多行，列表可自然分行。不需要转义、不需要括号配对，也就没有「JSON 语法」这一类失败面。
- **导入入口不再发送 `json_schema`**，每段只有一次模型调用（原先还有「结构化被拒 → 降级重试」的第二笔调用），费用与延迟都更低。
- **通用规范化层 `model-json-normalizer.mjs` 负责把输出变成结构化数据**：模型照记录格式写就按字段清单解析；模型仍写 JSON（含围栏、散文、未转义换行、尾逗号、注释、全角标点、输出截断、JSONL、字符串里套 JSON）就尽量修回来。它只修**语法**，不补字段、不改写措辞、不把缺失值编造成事实。
- 规范化动作与结果对作者可见：段级告警带模型原文片段；被截断的输出记 `OUTPUT_TRUNCATED` 并说明「只保住了完整条目」；响应里的 `normalization.repairedChunks` 在预览头部显示「规范化 N 段」。
- 这一层与功能无关，其它模型入口若也遇到「模型写不好 JSON」应复用它，而不是各写一套修复逻辑；设定助手与卡牌入口输出小、单条，仍保留 `json_schema` + 宽松收敛。

代价与取舍：记录格式比 JSON 更依赖模型遵守字段名，字段名不匹配会落到「续行」而不是新字段；为此字段清单 `IMPORT_RECORD_FIELDS` 与提示词由测试强制一致，未知标签按续行处理以免丢正文。**不采用 LLM 规范化 agent**：那要多一次付费调用，且可能改写内容，与「只搬运作者原文」的纪律冲突。若将来出现记录格式也无法解析的输出，再考虑把它作为显式、可计费的兜底选项。

### 10.1 后续实测暴露的供应商侧两个坑

同一轮实测里，「空内容」在记录格式上线后仍然出现，因此补了两层与协议有关的兜底：

- **思考预算**：`deepseek-flash` 这类思考型模型会把输出预算耗在推理上，正文直接为空。所有机械型入口（导入、设定候选、卡牌补丁、名称生成、宏观提案、提示词优化）现在默认发送 `thinking: {type: 'disabled'}`；供应商若不认这个参数（400/422），调用层去掉它重试一次并在进程内记住。自由对话保留供应商默认，因为那里推理可能有用。
- **响应形状**：网关可能把正文放在另一套形状里（chat 请求回 `output[]`、或把整个响应再包一层 `data`）。服务端解析一次覆盖 chat `choices[]`、responses `output_text`/`output[]`、顶层 `text`/`completion` 与包装层；仍然为空时，**首段**换另一种 API 类型（chat ↔ responses）重试一次，成功则整次请求沿用它，并记 `STYLE_FALLBACK` 提示作者去设置里改「API 类型」。
- 空响应不再是一句「不是 JSON」：错误信息里带 `style`、`finish_reason`、实际返回字段名与 `reasoning_content` 字数，作者与维护者都能直接判断是 key 错位、模型思考还是配置错。

这三条都是**协议兼容层**，不改变内容纪律：不猜内容、不把推理过程当资料、不静默改配置（只在本次请求内切换并告警）。

## 备选方案与代价

- **一次调用整篇**：超出上下文窗口，费用与耗时不可控，任何一次失败全部丢失。否决。
- **服务端缓存解析计划、只回传选择**：省带宽，但重启即丢计划，多用户下还要做归属与过期；改为客户端回传整份条目，信任级别与 `PUT /api/content` 相同（都有会话与标记头）。
- **用一次 LLM 归并**：质量可能更高，但多一次付费调用、结果不可复现。否决；同名合并留给确定性规则。
- **直接写 canon**：违反作者主权与 ADR-0025。否决。
- **复用 `/api/import`**：需要先有交换格式 JSON，且是管理员整库覆盖语义，与「建立新世界」不符。否决。

## 验证

- `tests/lore-import.test.mjs`：18 项纯函数测试（截断与切分确定性、提示词 4→5→6 顺序与记录格式契约、字段清单、模型输出收敛、记录格式落成条目、JSON 围栏 / 换行 / 尾逗号 / 截断恢复、空响应诊断、跨段合并、编号、改写、落库复核）。
- `tests/lore-import-api.test.mjs`：16 项端到端测试（真实 `server.mjs` + 本地假模型）：记录格式一次调用即落成条目且**不发送 `json_schema`**、默认发送 `thinking:{type:'disabled'}`、供应商拒绝该参数时去掉重试并记住、chat 请求读到 responses 形状的正文、首段空内容时切换 API 类型并记 `STYLE_FALLBACK`、只有 `reasoning_content` 时的诊断、分段调用与不写库、未知 preset 前置 400、全部段落失败报错、确认导入只追加、编号冲突 409、结构不合格 400，以及文件读取路由（缺标记 403、DOCX+ZIP 转文本、不写库不计模型调用、坏 base64 400、RAR 明确拒绝）、模型输出未转义换行仍能落成条目、不可解析 / 空内容时告警带原文片段。
- `tests/model-json-normalizer.test.mjs`：11 项规范化层测试（合法 JSON 原样通过、围栏与散文、未转义换行、尾逗号 / 注释 / 全角标点、截断恢复、JSONL、双层 JSON、不可解析返回 `undefined`、记录格式的段落 / 多行 / 列表 / 数字 / 占位词 / `##` 与 `【】` 标记、JSON 优先于记录格式）。
- `tests/lore-import-files.test.mjs`：13 项文件输入层测试（真实 ZIP/DOCX/XLSX/OLE2/RTF 字节夹具）：编码识别、按签名识别格式、DOCX 段落/表格/脚注、XLSX 多表与共享字符串、压缩包内格式校验与预算（路径穿越、加密、炸弹、嵌套深度）、旧版 doc 尽力抽取、RAR/PDF 拒绝、超长截断与上传边界。
- `tests/subpath-routing.test.mjs`：界面入口、预览控件、文件读取与请求契约断言。
- **未验证**：真实模型对长文的分段质量与错误率、真实导入后在浏览器里的地理树 / 年表渲染、真实 Word/WPS 导出的 `.doc` 与 Python/Java 生成库导出的 `.docx` / `.xlsx` 的兼容面、真实压缩包（含加密、分卷、ZIP64）的处理。这些需要作者实测，本文不声称已验证。

## 未决问题

- 是否允许把解析结果并入**已有世界**（当前只建新世界）。
- 是否把「设定导入」暴露为 DSH preset 侧的入口或工具。
