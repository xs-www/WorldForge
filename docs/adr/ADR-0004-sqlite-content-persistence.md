# ADR-0004：使用 SQLite 持久化创作内容

- 状态：canon
- 日期：2026-10-13
- 决策者：作者
- 来源：作者要求 Worldforge 作为后续游戏的世界观基底

## 背景

设定、卡牌、关键词与备注原先只按浏览器 Origin 保存在 `localStorage`。本机地址与 Tailscale 地址因此拥有互不相通的数据，换浏览器或设备也无法读取同一份世界观资料。这不适合作为后续游戏和内容工具共享的数据基底。

## 候选方案与代价

1. 继续使用 `localStorage`：实现最简单，但无法跨地址与设备共享，也缺少集中备份入口。
2. 使用 JSON 文件：依赖少，但并发更新、查询、迁移和数据完整性较弱。
3. 使用 SQLite：单文件、事务化、可查询、便于备份，适合单作者和小型团队逐步扩展；代价是需要维护 Schema 版本与写入冲突处理。

## 决策

1. 使用 SQLite 作为运行中创作内容的权威存储，数据库位于 Docker 持久化卷 `/data/worldforge.sqlite`。
2. 分表保存设定、卡牌、关键词与备注；常用分类字段独立成列，完整对象保留为 JSON，以兼顾查询与现有数据契约。
3. 浏览器 `localStorage` 降级为缓存和旧数据迁移来源，不再作为跨地址共享的权威数据源。
4. 数据库未初始化时，首个包含旧内容的浏览器自动迁移；后续 Origin 的旧内容按稳定 ID 合并，并在覆盖缓存前保存浏览器内备份。
5. 保存使用递增 revision 做乐观并发检查；发现过期写入时拒绝覆盖并提示先导出、刷新。
6. SQLite 内容仍是运行时草案库，不自动写入 Git，也不改变 `canon` / `proposed` / `unknown` 的作者裁定流程。

## 影响范围

- `storage.mjs` 与 `server.mjs`
- Docker 镜像、健康检查、Compose 持久化卷
- HTML 编辑器启动、缓存、保存状态和完整 JSON 导出
- Node.js 最低版本提升至 22.5
- `/api/health` 与 `/api/content` 服务端接口

## 未解决问题

- 尚未提供数据库快照下载、定时备份和一键恢复界面。
- 尚未实现多人实时协作；当前只通过 revision 阻止静默覆盖。
- SQLite 与仓库 Markdown/YAML 正史文件之间仍需人工审核流程。
