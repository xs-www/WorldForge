# Worldforge：原创宇宙与卡牌设计工作台 — 项目设计文档

**版本**：0.1.0（提案）  
**状态**：供 Codex 初始化仓库  
**类型**：Git 管理的 Markdown + YAML 内容项目，后续可扩展校验器/浏览器  
**第一世界**：W01，魔导工业（暂名“以太炉纪元”，未确认为正史）

## 1. 背景与目标

创作者希望拥有独立、可长期扩展的原创神性多文明宇宙，能够同时为类炉石卡牌对战、自走棋等策略作品提供世界观和可复用机制素材。首个世界选择蒸汽与魔法深度融合的魔导工业文明；神性受诺斯替主义等思想启发，但不复制《原神》《星穹铁道》《战锤》或魔兽 IP 的具体神系、名词组合和作品内容。

其他项目如合作项目“武林戏”、TNF、渔歌唱晚、跳水教练、幕布校园及 Digi Muse 不应被默认纳入该宇宙。本项目不是游戏运行时、不是完整卡牌客户端；AI 生成图仅作为带来源记录的 `proposed` 候选，不代表已获得商用授权。生图请求必须携带可追踪请求 ID；连接中断时只允许查询同一请求已持久化的结果，不自动重复调用可能收费的生成服务。

### 目标
1. 建立版本化、可追溯、可逐渐晋升正史的宇宙设定库。
2. 将世界观拆解为文明、人物、势力、技术、神性和事件等可索引资产。
3. 建立具备严格术语、可机器校验的卡牌规格与关键词规范。
4. 让 Codex 能够执行“草拟→冲突检查→人审→定稿→批量衍生”的工作流程。
5. 支持未来导出卡牌清单为 JSON/CSV，供独立游戏客户端读取。

### 非目标（首期）
- 不实现联网对战、可执行游戏客户端或自动全量数值平衡；卡牌编辑器与美术生成只服务于内容草案。
- 不自动确定宇宙终极真相；不一次生成百位神与几百张成套卡牌。

## 2. 设计基线与待决定事项

| 事项 | 当前状态 | 说明 |
|---|---|---|
| 原创独立宇宙 | 已确认方向 | 不依附武林戏/魔兽等第三方世界观 |
| 多世界、多文明、神性 | 已确认方向 | 神既可作为信仰对象也可成为研究对象 |
| W01 魔导工业 | canon | 蒸汽与魔法长期共存；近代魔导工艺是传统施法的工程化实现 |
| 以太与魔力 | canon | 同一能量的游离态与固化态；能量总量守恒 |
| 蕴魔矿与蓄魔器 | canon | 前者天然含魔力，后者可接受外部供能并重复储放 |
| 施法与魔导器 | canon | 咒语只含派系与效果；设备外部补齐时空上下文和魔力流向 |
| 高层神性规则 | unknown | 人格神、神的来源、权能边界与以太关系尚未裁定 |
| 神系与势力名称 | proposed | 不自动锁定“守律者”等此前示例 |
| 卡牌基础信息 | canon | 随从为费用/攻击/生命，法术仅费用，武器为费用/攻击/耐久；见 ADR-0001、ADR-0016 |
| 类炉石战斗规则 | 待定 | W97 已有 `experimental / untested` 可玩纵切，但未锁定正式费用、卡组张数、时序和胜负条件 |
| 具体原创关键词 | proposed / experimental | W97 暂用疾启、护持、隔绝、余响验证四类受控语义；未批准为正式词典 |

**必须区分**：`canon`（作者批准）、`proposed`（草案）、`deprecated`（废弃）；以及 `objective`（设定事实）、`in_world_belief`（世界内的传说或观点）、`unknown`（有意保留）。

宏观世界采用“规则维护权威状态、LLM 提供局部行动提案”的分层边界，见 [ADR-0015](adr/ADR-0015-macro-rules-local-llm.md)。W98 群陆只用于多地区季度演化与地图交互验收，不得作为 W01 或宇宙设定引用；其所有数值均为未经平衡的实验参数。

## 4. 内容数据规范

### 4.1 Lore 条目示例
```yaml
id: FAC-W01-001
name: 示例工业联盟
status: proposed
truth_scope: objective
world_id: W01
summary: 由多个工业城市组成的政治和经济合作组织（占位示例）。
dependencies: []
open_questions:
  - 工业联盟是否拥有独立军队？
sources_or_inspirations: []
```

### 4.2 卡牌 YAML 最小规范
```yaml
id: CARD-W01-0001
name: 高压守卫
status: proposed
world_id: W01
set_id: W01-PROTOTYPE
faction_ids: []
card_type: minion
cost: 3
stats:
  attack: 3
  health: 4
rarity: common
tribe: null          # 随从种族；法术用 spell_school，武器两者都为 null
keywords:
  - id: KEY-001
    detail: "本卡对该关键词的可选附加说明"
effects:
  - trigger: on_turn_start
    condition: "本单位在场且可生效（规则待审）"
    target: self
    operation: add_counter
    args: {counter: pressure, amount: 1}
    duration: permanent_while_in_play
rules_text: "你的回合开始时，获得1点压力。"
flavor_text: ""
balance_status: untested
lore_refs:
  - CHR-W01-001
notes:
  - 示例卡，只测试数据格式；压力用途尚未确定。
```

建议将执行逻辑与展示文案分开；`effects` 是结构化设计描述，不意味着已有可执行引擎。实现前需正式定义允许的 trigger/operation/target 集合，避免不受控自由文本成为伪结构化数据。卡牌类型固定为 `minion / spell / equipment`（随从 / 法术 / 武器）：随从 stats 为攻击与生命，法术 stats 为空对象，武器 stats 为攻击与耐久。稀有度固定为 `common / rare / epic / legendary`（普通 / 稀有 / 史诗 / 传说）。随从可带 `tribe`（种族），法术可带 `spell_school`（派系），两者互斥且武器均不适用；法术派系沿用 W01 canon 的十一种魔法派系，随从种族词表仍为 `proposed` 候选，详见 [ADR-0017](adr/ADR-0017-minion-tribe-and-spell-school.md)。`lore_refs` 可保留多个设定来源，但创建卡牌草案不会改变来源条目或卡牌的 `proposed` 状态。

### 4.3 关键词规范
每个关键词至少包含：
- ID / 名称 / 设计意图 / 所属范围；
- 可读规则文本与机器语义草案；
- 触发时机、优先级、目标条件、持续时间与叠加规则；
- 使用示例、反制方式、边界案例、已知风险、测试清单；
- 对已有术语的依赖及与其他关键词的联动。

关键词定义保存通用语义；卡牌引用可携带可选 `detail`。无 `detail` 时显示关键词名称，有 `detail` 时显示为“关键词：附加说明”。编辑器保持逐项输入；卡面编译时按独立关键词、带说明关键词、普通文本的优先级汇入同一规则框，关键词名加粗并由排版器自动换行。关键词附加说明和普通文本允许 `<b>...</b>` / `**...**` 粗体与 `<i>...</i>` / `*...*` 斜体；编译器只识别这四种标记，其他 HTML 必须作为普通文字处理且不得执行。该附加说明只属于当前卡牌，不修改关键词定义。

### 4.4 一致性与索引
每条设定有稳定 ID；引用使用 ID + 相对链接；事实冲突应记录为 issue 而不是自动“圆设定”。同名异义、单位换名及重大设定推翻必须保留历史记录。

资料以 `world_id` 归属到具体世界，世界观界面据此分为“世界列表 → 世界内资料”两级：同一世界的资料不会与其他世界混列，关联引用跨世界时单独成组。没有有效 `world_id` 归属的旧数据进入未归属面板等待作者归入，不自动猜测。详见 [ADR-0019](adr/ADR-0019-world-hub-two-level-navigation.md)。

关联资料的选择使用独立分栏窗口：一侧是可搜索、可按类型/世界/状态过滤的全量资料池，另一侧是实时更新的已选关联；当前编辑中的条目不会出现在池中，取消会丢弃草稿。关联仍是稳定 ID 数组，不引入层级或权重语义。详见 [ADR-0020](adr/ADR-0020-filtered-relation-picker.md)。

地理条目使用 `LOC-W##-###`，并以稳定 `parent_id` 形成世界内的层级树。大陆直接属于世界；国家必须属于大陆；地区、区域、城市、地点与路线必须引用同一世界内允许的上级，界面不得把不同层级平铺。缺少有效上级的旧数据应进入待整理区，不自动猜测归属。地图图像、边界几何与坐标系统属于后续可视化能力，不影响当前地理层级作为内容源。

### 4.5 背景故事

- 背景故事使用 `STORY-W##-####`，作为独立资料而不是人物、地点正文中的不可索引长字段。
- 一个设定条目可以被多篇故事引用；一篇故事也可以关联多个设定条目或其他故事。
- 故事在内容上只有标题与正文；ID、世界和关联属于内部管理字段。故事不使用摘要、约束、开放问题、标签或类型专属属性。
- 故事内部固定保持 `proposed / unknown`，但这些技术状态不出现在故事编辑界面。叙述内容不自动等于 `objective canon`，其中出现的新事实仍需单独裁定。
- 鼓励从传记、轶事、局部事件和具体场景逐步生长世界；不要求先完成全局百科式设定。

### 4.6 AI 提示词与示例层

- 固定项目安全边界、作者可编辑的类型提示、统一个性化风格、自动 canon 示例和本次临时示例必须分层组合；可编辑提示不得替换 canon 审核与原创性边界。
- 13 类设定各自拥有独立提示词，允许作者在设置页精调或恢复默认值；统一个性化提示用于文风、叙事视角、篇幅和审美导向。
- 自动示例只选择同一世界、同一类型、状态为 `canon` 的条目，并受数量和字符预算限制。示例用于风格与结构参照，不代表可以复制内容或覆盖当前约束。
- 作者可在每次生成前添加临时示例；临时示例只进入当次请求，不写入资料库或提示词设置。
- 模块助手不再共享一套固定候选字段。每类资料声明自己的可生成内容块；作者可以只选择其中一部分，服务端按选择构造严格 Schema，未选择字段由当前表单保留。
- 候选响应按条目独立校验，已通过条目不会因同批其他条目失败而丢失；数量不足时仅补充差额。校验错误与截断后的模型原始片段返回给作者查看，补充仍失败时以部分结果呈现，不伪装为完整成功。
- 单份候选可显式应用到当前编辑表单，只覆盖本次返回的内容块，仍需作者点击保存；多份候选仍可另存为独立 `proposed` 草案。背景故事候选应用时打开未保存的故事表单，不覆盖来源条目。
- 世界地图的 `details` 块在界面和服务端契约中统一称为“详细设定”，与编辑器正文栏一一对应；“环境与交通”继续作为独立短字段。
- 生成内容必须是可直接回填的成品文字，不把“层次位置”“本候选”“设计意图”“约束字段说明”等元信息混入正文。
- 自由创作 Agent 是独立的非结构化对话入口，可接收作者需求、关联信息及可选资料库索引；它不复用模块候选 Schema，也不会自动写入资料库。

### 4.7 编年史

- `timeline` 资料采用两级结构：`chronicle` 是编年史容器，`entry` 是隶属于某部编年史的记录节点；旧时间线在缺少新字段时按容器兼容。
- 节点保存面向读者的纪年文本与独立数值排序字段。纪年文本可使用虚构历法、纪元或不确定日期，排序值只表达先后，不替代正文中的历法说明。
- 节点必须引用同一世界的编年史容器，并可通过普通资料关联指向事件、人物、地点或势力；编年记录不会自动把关联内容晋升为 canon。
- 搜索命中节点时保留所属编年史；删除仍含节点的编年史必须被阻止。

## 5. 典型 Agent 工作流

### A. 设计世界设定
1. 读取宇宙级 canon、W01 现有规则及相关 ADR。
2. 列出现有约束，补充 2–3 套可行方案及各自代价。
3. 产出 `proposed` 草案、依赖、反例和未解决问题。
4. 仅在用户批准后改为 `canon`；更新索引、变更记录。

### B. 生成卡牌
1. 确认当前基础对战规则版本、主题、卡牌数量、目标派系、机制预算。
2. 阅读已有关键词，优先复用；新增关键词需单独规范。
3. 先生成小批量候选卡（建议 5–10 张）。
4. 检查文本统一、触发边界、无穷循环、无限资源、胜利条件绕过、卡牌重复定位。
5. 输出数据 YAML + 人可读卡牌清单 + 设计说明 + 风险报告。
6. 经用户审阅后批量扩展；只可将数值标记为 `untested` 或真实测试状态。

### C. 审核旧卡牌扩展包
1. 将用户原文作为仅供参考的设计资产，标记来源与 IP 风险。
2. 拆出通用机制、用户原创机制、依附第三方叙事的内容。
3. 先完成原创世界中的叙事和机制再创作，避免简单替换专有名称。
4. 评估相似性、规则依赖与新世界观契合程度。

### D. 世界观冲突审计
报告按严重程度区分：
- BLOCKER：否定已批准底层事实或导致逻辑不可成立；
- MAJOR：资源/运输/神性/时间线严重不协调；
- MINOR：措辞、别名、细节不一致；
- OPEN：作者刻意保留的谜团，不等同于错误。

## 6. 校验与质量门槛

### 首期（纯文档）
- Markdown 文件无断链（能检查时）；ID 唯一；所有条目状态合法。
- 卡牌基础字段齐全、数值非负、关键词引用存在。
- 机制描述包含明确的目标与时机，没有显见互斥条件。
- 数据文件区分 lore 引用与游戏规则引用。

### 后续（工具化）
- JSON Schema 验证 YAML；生成唯一 ID 索引与引用图。
- 检测引用缺失、循环依赖、异常费用曲线、重复机制。
- 卡牌规则事件模拟器仅在已形成正式 timing specification 后实现。
- 可导出 CSV/JSON 供游戏客户端使用，但不把本仓库绑定某一引擎。
